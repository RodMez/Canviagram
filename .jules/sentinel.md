## 2024-10-08 - [Timing Attack in Secret Comparison]
**Vulnerability:** The API endpoint `app/api/reminders/run/route.ts` compared the provided `x-reminder-sweep-secret` header against the expected secret (`env.REMINDER_SWEEP_SECRET`) using a simple string equality check (`!==`).
**Learning:** Simple string equality comparison (`===` or `!==`) returns early upon finding the first mismatched character. This allows attackers to deduce the secret character by character by measuring the response time, which is known as a timing attack.
**Prevention:** Use a timing-safe equality comparison function, such as `timingSafeEqual` from the `crypto` module (Node.js standard library), which compares strings in constant time. Make sure to check the lengths first before passing the buffers to `timingSafeEqual`, as it throws an error if lengths do not match.

## 2024-11-10 - [Invalid Bcrypt Dummy Hash Re-introduces Timing Vulnerability]
**Vulnerability:** The API endpoint `app/api/auth/login/route.ts` used a dummy bcrypt hash `'$2a$10$dummyhashdummyhashdummyhashdummyha'` to mitigate user enumeration timing attacks. Because it is mathematically invalid in base64 encoding/format, `bcrypt` rejected it immediately before doing any hashing logic, making the fake check run in a fraction of a millisecond instead of ~120ms. Attackers could still enumerate users because true user comparisons took significantly longer than missing user comparisons.
**Learning:** Functions meant for side-channel mitigation using mathematical or string parsing libraries must be given mathematically and functionally valid values that actually engage the targeted cryptographic workload. Invalid data causes early returns, reintroducing the timing vulnerability it intended to fix.
**Prevention:** Generate dummy hashes that are valid outputs of the algorithm (e.g. `const dummy = bcrypt.hashSync('dummy', 10);`), so that the library is forced to do a full workload computation when checking against the attacker's password.
